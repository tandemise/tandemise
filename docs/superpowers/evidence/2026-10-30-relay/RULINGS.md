# Relay build: rulings

Where the plan (`docs/superpowers/plans/2026-10-30-relay.md`) was ambiguous or
disagreed with the spec (`docs/superpowers/specs/2026-10-30-relay-design.md`,
binding), the builder decided from the spec and recorded it here.

- Ruling (Task 1): `RelaySnapshot` also carries `you: { memberId, deviceId, role }`, so a daemon can tell its own claims and its relay role apart without a second request. Additive, within "exact route payloads" left to the builder.
- Ruling (Task 2): `takeOverRefusal` also takes `holderMemberId`; without it "This is already yours." can't be decided. The `heldBySentence` check uses `startedAt: '…T10:42:00Z'` because a zone-less ISO string parses as machine-local time and the pinned "10:42" (in UTC) would depend on the test machine's zone.
- Ruling (Task 2): `check-boundaries` judges a subpath import (`@tandemise/api-contract/relay`) as its package, so `coordination` can depend on the zod-only subpath the spec names instead of the package root, which would pull `domain` into the relay at runtime.
- Ruling (Task 2): the `coord_*` tables carry no foreign keys and `coord_devices.token_hash` is nullable, so a daemon's mirror can hold a relay claim whose device it has never seen (it stores the device label without a token).
- Ruling (Task 4, scope): **no persistence migration 025.** The spec (binding) says "The daemon's `MIGRATIONS` list is not touched, so the two version streams can't tangle" and that both relay and daemon call `migrateCoordination(db)` at boot. The plan's 025 also can't land: `assertOrdered` needs a contiguous list and 022–024 (hold-and-interact, brain, intake) are not on `main`, while the plan forbids renumbering. So the daemon gets the shared tables from `migrateCoordination(db.handle)` at boot, and the two daemon-only tables (`coord_outbox`, `coord_claim_sync`, exactly as the plan specifies them) come from a second coordination stream, `migrateCoordinationDaemon`, recorded in `coord_meta.daemon_schema_version`. The `parity` section proves the daemon's boot path yields byte-identical shared tables and indexes, the daemon-only tables exist only there, a second boot is a no-op, and persistence's `MIGRATIONS` has nothing coordination in it. This also removes the migration-number clash with the parallel features at merge.
- Ruling (Task 5): the approval path's claim runs in `ApprovalServiceImpl.decide`, before the decision's transaction, not inside `#resumePlan`: `#resumePlan` is synchronous and inside the transaction, and the plan requires the card to stay PENDING on a refusal. A replan's card (a plan proposal) does not claim; its mission already started.
- Ruling (Task 5): `MissionService.start` claims only when the mission may move to EXECUTING (`canTransition`), so a start that would fail anyway leaves no claim behind.
- Ruling (Task 5): `details.takeOver` on a start refusal comes from `ClaimResult.held_by.mayTakeOver`, decided where the claim lives (the local store, or the relay, which knows its own clock and who was seen when), instead of the daemon re-running `takeOverRefusal` against a mirror whose clock can differ from the relay's.
- Ruling (Task 5): a background claim (backstop) that finds the item held records `coord_claim_sync` under the id `lost:<missionId>` (port method `markLost`), since there is no own claim row to attach the note to. The port also gained `me()`, `holderLastSeenAt()` and `claimByLocalRef()` so the service can build rows and banners from local reads only.
- Ruling (Task 5): `application` depends on `@tandemise/coordination` (L5 → L3) for the pure rules (`githubItemRef`, `itemKey`, `takeOverRefusal`, `lastSeenLabel`); it still never names an implementation. `ProjectionTopic` gained `coordination`, and the desktop's `TOPIC_KEYS` got its entry in the same task so the desktop typecheck stays green.
- Ruling (Task 5): the check uses `acme/app#7` in the take-over sentence (the plan's `ACME-123` example) because the harness's tracker is GitHub.
- Ruling (Task 6): a local hook without the daemon token answers **403**, not the plan's 401: that is the daemon's existing envelope for a missing or wrong token (`PERMISSION_DENIED`), and the check pins the daemon's real behaviour.
- Ruling (Task 6): `onChange` reaches `PROJECTION_BUS.invalidate('coordination')` through `CoordinationService` (which subscribes in its constructor) rather than a second forward in bootstrap, so a harness without bootstrap gets the same invalidations. `RequestContext` gained `res`, so the export (NDJSON) and the hook ingress (202, handshake bodies) can answer with something other than JSON (`HANDLED` existed but had no way to write).
- Ruling (Task 6): the daemon's own requests are `connectRelayRequest`, `projectKeyRequest` (`{ workspaceId? , projectKey? }`), `takeOverClaimRequest` (`{ missionId }`), `coordinationPullRequest` and `coordinationEndpointRequest` (an endpoint for a workspace's project or a project key), since the desktop knows workspaces, not project keys.
- Ruling (Task 7): the start refusal is a dialog (`ClaimRefusal`, a `Modal` titled "Someone is working on this") with **Take over** when allowed and **Not now**, not an approval `Decision`: it is not an approval. On the approval path the error is rendered where approval errors already render, `components/Decision.tsx` (shared by the Inbox and the feed), through `ClaimAwareError`; `ApprovalCard.tsx` itself needed no change.
- Ruling (Task 7): r01 links its missions to `acme/app#7` by writing `issue_links` and `missions.issue_link_id` into the window's daemon database (as issue sync would), and starts them through the real plan approval in the Inbox. How a mission comes from an issue is P14's subject and is proven there. The scenarios use a new one-person-step workflow (`scratch/acceptance/p0/workflows/relay-person.yaml`) so a mission keeps running until its step is finished.
- Ruling (Task 8): "seen" for staleness is an authenticated request (throttled touch) or a presence change, not merely an open socket; `holderLastSeenAt` is the newest of the member's devices' `last_seen_at` and presence rows. Spec: "A claim is stale when none of its holder's devices has been seen for `RELAY_STALE_AFTER`". A connected daemon re-reads its snapshot every few minutes (Task 11), which counts as seen, so in real time a connected holder is never stale; with the test clock moved 25 h, an idle holder is, which is what r05 needs.
- Ruling (Task 8): a `409 claim_held` carries `details.takeOver` (whether *this caller* may take over, by the relay's clock), and the snapshot carries `serverTime` and `staleAfterMs`, so daemons judge staleness by the relay's time. Failed auth (bad token, bad invite code) locks an address after the tenth failure in a minute: the 10th is still 401, the 11th is 429.
- Ruling (Task 8): the test-clock route exists only with `RELAY_TEST_CLOCK=1` (otherwise an unknown route, 404). Health is exempt from the version header (Docker's HEALTHCHECK sends none); every other route and the stream upgrade require it.
- Ruling (Task 10): the example settings ship as `apps/relay/env.example`, not `.env.example`: this build environment refuses to write `.env*` files. `compose.yaml` takes every variable through `environment:` with `${VAR:-default}` interpolation (Compose reads `apps/relay/.env` for that automatically, or the shell), instead of `env_file: .env`, so it also works without a `.env` and fails clearly when `RELAY_PUBLIC_URL` is missing.
- Ruling (Task 10): the image is `node:22-bookworm-slim` as the spec says, and that base alone is about 200 MB unpacked, so "under 120 MB" is held as the **compressed** size a pull downloads (`docker save | gzip | wc -c`, measured 84 MB); CI asserts that. The Dockerfile ignore file is `apps/relay/Dockerfile.dockerignore` (BuildKit's per-Dockerfile ignore) rather than a root `.dockerignore`. The build stage skips the plan's `npm rebuild better-sqlite3`: nothing runs SQLite there; the runtime stage rebuilds it from its prebuilt binary.
- Ruling (Task 10): release-please now also bumps `packages/coordination` and `apps/relay` versions (package.json and lockfile), like every other workspace.
- Ruling (Task 11): the relay client opens its stream with the `ws` package (already a repo dependency), not Node 22's global `WebSocket`, which can't set handshake headers; the token stays in the `Authorization` header. `coordination-relay` declares `ws`.
- Ruling (Task 11): on connect, the person's own active local claims become provisional relay claims queued in the outbox (normal claim semantics, conflicts reported per item), and the relay's `import` treats a relay as "empty" when its only claims are the importer's own. That reconciles the spec's two paths (automatic own-claims push on a non-empty relay; "Bring my local data" on an empty one): the import re-sends those claims idempotently and adds the endpoints and unread webhooks.
- Ruling (Task 11, scope): the default project key is the workspace's first repository remote, normalised (`github.com/acme/app`), before falling back to the workspace id; `GET/PUT /v1/coordination/project-key` sets it explicitly. Without this, two people's installs of one repository could never see each other's claims until #51 lands, because their workspace ids differ. The acceptance run sets it explicitly on both windows.
- Ruling (Task 11): a connected daemon re-reads its snapshot every 5 minutes (which keeps it "seen"), sends presence only on a change, and judges staleness on the relay's clock (`serverTime` offset). An own claim that disappears from a snapshot has its fate read from the item's history, so a take-over or removal shows as Unclaimed.
- Ruling (Task 12): Settings → Team relay also lists webhooks that couldn't be processed with Retry and Drop, through `GET /v1/coordination/messages/parked` (relay: `GET /relay/v1/mailbox/parked`), since the plan names the buttons but no way to list the messages.
- Ruling (controller, review of #69): the compressed 120 MB image measure is accepted; the spec's Deployment line now says "120 MB compressed" and why (the chosen base alone is about 200 MB unpacked).
- Ruling (controller, review of #69): the project key defaulting to the repository remote is accepted; the spec's Data model paragraph says so. The computed key is persisted into `coordination.projectKeys[workspaceId]` on first use, so it can't drift.
- Ruling (controller, review of #69): TLS is safe by construction. The `tls` profile is replaced by an override file, `apps/relay/compose.tls.yaml` (`docker compose -f compose.yaml -f compose.tls.yaml up -d`), which adds Caddy and, for the relay, replaces its port with `127.0.0.1:${RELAY_PORT}:8787` (`ports: !override`) and sets `RELAY_BIND=127.0.0.1` and `RELAY_TRUST_PROXY=1`. Verified with `docker compose -f compose.yaml -f compose.tls.yaml config`: the relay's only published port has `host_ip: 127.0.0.1` and `RELAY_TRUST_PROXY: "1"`; the plain `compose.yaml` publishes on all addresses and has no trust-proxy. `X-Forwarded-For` is ignored unless `RELAY_TRUST_PROXY=1`.
- Ruling (review of #69): on Disconnect the daemon first tries to drain the outbox for up to 3 s; what is still unsent is kept in `coord_outbox`, marked "Not sent: you disconnected before the team relay heard about it.", and listed in Settings (nothing is deleted).
- Ruling (review of #69): `import` accepts bodies up to the mailbox cap × 4/3 (base64) + 16 MiB; export lines are validated with zod (`coordinationExportLine`), so a malformed file is a 400 `import_invalid`. Removing the last admin is refused (409 `last_admin`). The application imports only `@tandemise/coordination/rules` (enforced by check-boundaries).
- Ruling (Task 1): a take-over request body is `takeOverRequest { localRef }`, so the taker's daemon can tie the new claim to its own mission. The plan's route list names the route but no body.
