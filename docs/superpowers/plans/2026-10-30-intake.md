# Intake Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Anything that might be work, from any source, is recorded and lands as one item in the project's primary tracker (created or linked, never duplicated). A person starts an item from the board, and only then does a mission exist. The tracker follows the mission through one activity comment and mapped state changes, and the loop closes at every source when the item is done.

**Architecture:** One contract, `tandemise.intake/v1` (zod in `api-contract`, pure rules in `domain`). One pipeline, `IntakeService.ingest`: validate, record, filter noise, dedupe, then create or link. It talks to the tracker only through a `PrimaryTracker` port, with a YouTrack adapter (new `integration-youtrack`, REST over `fetch`) and a GitHub Issues adapter (`integration-github`, over `gh`). `TrackerService` keeps a board cache, handles Start through `MissionService.create`, and writes state and the activity comment back. `ClosureService` closes the loop through each runner's `close`. Runners implement an `IntakeRunner` port and register through a `multiToken`: GitHub (P14 migrated) in `integration-github`; Sentry, PostHog, Slack and Discord in the new `intake-runners` package. Custom runners push over a loopback HTTP route or a new `tandemise` CLI. Configuration is read through an `IntakeConfigSource` port. A local-settings implementation ships now, and the brain (#51) plugs in later.

**Tech Stack:** TypeScript, Node 22 (built-in `fetch` and `WebSocket`), better-sqlite3, zod 3, React 18, Electron 44. No new runtime dependency. The fakes in `scratch/` use `ws` (already a daemon dependency) for the Slack and Discord socket servers.

**Spec:** `docs/superpowers/specs/2026-10-30-intake-design.md`. It is binding; read it first. This plan argues from it and names its sections as "spec §n".

## Global Constraints

- **Migration number is 024** (rulings: hold-and-interact 022, brain 023, intake 024, relay coordination 025). `MIGRATIONS` must be contiguous (`assertOrdered`). Land Task 2 only after 022 and 023 are on `main`. If they aren't, finish Task 1 and stop to ask the owner. Never renumber, and never add placeholder migrations.
- **Intake creates no coordination tables.** The relay (#54) owns `coord_claims` and `coord_mailbox` (its own migration stream plus daemon 025) and the `CoordinationPort`. Intake defines two narrow ports instead:
  - `IntakeClaimsPort`, whose local default always grants, so the no-server path is the spec's "re-read the item and refuse if it is in progress";
  - `WebhookMailboxPort`, backed locally by `intake_webhook_inbox` and fed by the opt-in listener.
  
  The relay later supplies adapters for both. The spec's "Claims" acceptance bullet (two daemons sharing a lease) moves to #54; here a fake `IntakeClaimsPort` that refuses proves that runners and Start obey it.
- **Configuration only through `IntakeConfigSource`.** No service reads `settings.json` or a brain file directly. The file shapes (`trackerFileV1`, `intakeFileV1`) are zod schemas exported from `@tandemise/api-contract`, so the brain's codec parses `factory/tracker.yaml` and `factory/intake.yaml` with the same schemas.
- **Concurrent edits elsewhere.** Another feature is editing `packages/application/src/tokens.ts`, `engine/task-executor.ts` and desktop `TaskDetail.tsx`:
  - Do not touch `task-executor.ts` or `TaskDetail.tsx`.
  - Put every new application token in a new file, `packages/application/src/intake-tokens.ts`, re-exported from `index.ts`, so `tokens.ts` stays unchanged.
  - Edits to `module.ts`, `services.ts`, `scheduler.ts`, `mission-service.ts`, `projection-service.ts` and `routes.ts` are additive: new lines, no reshuffles.
- **Layer rules** (`npm run check:boundaries`):
  - `domain` holds the pure rules and ports;
  - `api-contract` holds the zod contract and file schemas;
  - `integrations-core` holds the `INTAKE_RUNNERS` and `PRIMARY_TRACKER_FACTORIES` multiTokens;
  - adapters and runners live in layer-4 provider packages;
  - the services live in `application`.
- **Text is data.** Signal text flows only into the tracker item's text (escaped through `escapeForComment` in comments) and, after Start, into the goal. No signal field can select a project, tracker, state, threshold or source.
- **Nothing in intake queues a mission.** Start calls `MissionService.create` with `queued` unset, and `planNow` true only when criteria were parsed.
- **Idempotent by key.** Everything is keyed: signals by `(workspace_id, fingerprint)`, links by `signal_id`, comments by `(item_ref, marker)`, closures by `(signal_id, kind)`. A link is written `pending` before the tracker call and `done` after it.
- **The API listener stays loopback-only.** The webhook listener is a separate, opt-in `127.0.0.1` server that serves only `POST /hooks/:sourceId`.
- **Credentials** live only in the local secret store (`SECRET_STORE`), never in a config file or the brain. Item refs follow the relay's normalisation, `<tracker>:<key>` (`youtrack:ACME-12`, `github:acme/web#42`).
- **UI copy** says "you", uses plain verbs and never shows raw enums. Colours come only from `palette.css`/`theme.css`, with no `var()` fallbacks. Use BEM classes and keep state in `data-*`. Refusals are `TandemiseError('CONFLICT' | 'PRECONDITION_FAILED', <sentence>)`, and the UI shows the daemon's own words.
- Repo artifacts are in English. Commit and PR titles are Conventional Commits with a lowercase subject. Run `npm run ci` before each PR.

## Review Focus

1. **Crash between the pending link and the tracker call.** The restart must search by exact URL before creating, so exactly one item exists whether the crash came before or after `create` returned. Pinned in Task 7.
2. **Two daemons racing on the same signal.** At most one item survives. The newer one is marked duplicate and its sources move over on the next board refresh, on both daemons. Pinned in Task 8.
3. **A person's tracker change always wins.** Write-back transitions only when the item is still in the state Tandemise last wrote, and never moves backwards except on cancel. Pinned in Task 9.
4. **Start never queues and never runs twice.** A second Start, or an item already in a mapped in-progress state, is refused with the exact sentence, and P7's `pull` never picks the mission. Pinned in Task 8.
5. **Closure is exactly-once per `(signal, kind)` across restarts.** Slack and Discord check the thread for their own reply first, and GitHub closes only with the setting on. Pinned in Tasks 11 to 13.

  5. Round to 2 decimals.

  2. **Dedupe:**
     1. A `done` link already exists → **`linked`**, with the sources comment updated only when the change matters (step 3).
     2. The URL is an item of the tracker. For github-issues, that is a GitHub issue URL in the tracker repo; the adapter answers `refFromUrl(url): TrackerRef | null`, an additive optional port member. Write a pending link with `source_is_item`, then complete it → **`linked`**.

     2. `tracker.create(createDraft(...))`.
     3. Complete the link with the real ref, and upsert `tracker_items`.

**Interfaces:**
- **`detect(ws, items)`:** for each item in a mapped `done` state, call `closures.ensure(signal, 'done')` for each linked signal. A `wont_do` item gets `ensure(signal, 'not_planned')` only when the source has `closeWontDo`. Signals move to `closure_pending`. This applies whoever moved the item, Tandemise or a person in the tracker.
- **`tick()`:** handles `due(now)` closures. It builds the `Closure`:
  - `prUrl` is the first pull-request `deliveryLinks` of the item's mission;
  - `commit` is the newest `git.commit` `sourceRefs` on the mission's artifacts, with `repo` from `githubRepoFromRemote` of the mission's repository; otherwise null.
  
  It hands the closure to the runner of the signal's kind. A custom kind has no runner, so its closure waits in the feed for an ack.
- **On a result:**
  - ok → `closed`, with `external_id` and `closed_at`; the signal becomes `closed`;
  - retryable failure → `attempts+1`, `next_attempt_at = now + min(60_000 * 2^(attempts-1), 3_600_000)`;
  - after attempt 8, or a non-retryable failure → `failed`, `last_error` set to the source's own words, and the signal becomes `closure_failed` with reason `"Couldn't close at <Label>: <error>"`.
- **`retry(id)`** resets the attempts and sets the closure back to `pending`.
- **Custom feed:** `listForSource(ws, sourceId, after)` returns `{ closures: [{ id, fingerprint, key, url, kind, item: { key, url }, prUrl }] }`. An ack with `ok:true` → `closed`. An ack with `ok:false` → `failed` with the error text.
